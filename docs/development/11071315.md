# Backendの容量圧迫解消に関して

## 現状と問題
容量を圧迫する原因はいくつか存在するが、特に以下の原因が挙げられる。

#### 1.収集DBにデータへのデータ蓄積
これが最大の圧迫要因である。サイズは約120GBであり、2分間の計測では、16.5MBが増加した。
ログを送信した後もDBの容量が解消されることはない。

#### 2.同じログの複数の型での保存
Syslog、DB内のRaw・Canonical、Wazuh向け正規化ログ、送信用アーカイブが存在する。
つまり、元ログ以上に他の形でのサイズでの保存量が増える。

#### 3.送信後のファイル
送信成功後も **sent.json** が残り続ける。

#### 4.未送信データの蓄積
転送が停止した中にもログを収集し続け、未送信データが蓄積されるので、容量を圧迫する。

## 解決策

#### 2,4についての対策
正規化ルールの見直しによってRawとCanonicalは区別する必要がなくなったので、Rawとして型を一つに統合する。
また、syslog,raw,Wazuh向け,送信用アーカイブの蓄積を回避するために各型の保存期間は72時間とする。

ここで、ディレクトリ構成について考えたい。
ディレクトリは型ごとに作成し、ディレクトリ内では日付ごとにディレクトリを作成する。
例を以下に示す。

```
Log/syslog
    |- /yyyymmdd
    |- /yyyymmdd

    /Raw
    |- /yyyymmdd

    /Wazuh
    |- /yyyymmdd

    /archive
    |- /yyyymmdd

    /sent
    |- /yyyymmdd/sent.json
```

以上のようにディレクトリを構成し、今日の日付とyyyymmddの日付を計算し、73時間以上の差がある場合は削除する。

次に考えるべきは、送信失敗時の処理である。上で説明したように処理していくと送信が連続で失敗し続けると、未送信のデータが削除され続ける可能性がある。

そこで、削除前にその日の送信をWSとBackend双方で確認する。その後、削除処理に移る。
これについてはsent.jsonとWSとBackendの双方でハッシュ値を用いて確認する仕組みにしたい。

#### 1についての対策
2,3,4への対策を実装した後で、容量を削除し圧迫問題を解決させたい。
