# ログ収集・AI解析自動化基盤 構築レポート

## 1. 目的

本作業では、卒業研究で構築しているAI-SOCシステムのログ収集・解析基盤について、各ハニーポットVPSで取得した攻撃ログを30分ごとにVPS1へ集約し、Gemini APIを用いて自動解析レポートを生成する仕組みを構築した。

最終的な構成は以下である。

- VPS1：ログ集約・Gemini解析
- VPS2：Web系Dionaea
- VPS3：DB系Dionaea
- VPS4：IoT系Dionaea

各VPSではDionaeaのログを正規化JSONへ変換し、VPS1へSSH/SCPで転送する。VPS1では受信した3種類のJSONをGeminiへ入力し、30分ごとのAI解析レポートを生成する。

# 4. VPS2で発生した主要問題

VPS2では今回の構築の中で最も多くの問題が発生した。

## 4.1 問題：古いSQLiteファイルを参照していた

当初のcollectorでは以下のSQLiteを使用していた。

```text
/tmp/dionaea.sqlite
```

しかし、このファイルはDionaeaコンテナ内のデータベースを過去にコピーしたものであり、現在の攻撃ログがリアルタイムで反映されていなかった。

そのため、

- Dionaeaログには新しいHTTPアクセスが存在する
- SQLite側にはその接続が存在しない
- ログとSQLiteから送信元IPを紐付けられない

という状態になった。

### 原因

実際にDionaeaが使用していたSQLiteはコンテナ内部の以下であった。

```text
/opt/dionaea/var/lib/dionaea/dionaea.sqlite
```

ホスト側 `/tmp/dionaea.sqlite` は単なる古いコピーであり、更新されていなかった。

### 対応

まずコンテナ内部のDBをバックアップした。

```bash
sudo docker cp \
dionaea-web:/opt/dionaea/var/lib/dionaea/dionaea.sqlite \
~/dionaea_backup.sqlite
```

次に、ホスト側へ永続化用ディレクトリを作成した。

```text
/home/ubuntu/honeypot/dionaea/data/
```

docker-compose.ymlへ以下を追加した。

```yaml
- ./dionaea/data:/opt/dionaea/var/lib/dionaea
```

これにより、Dionaeaが使用するSQLiteをホスト側から直接参照できるようになった。

---

## 4.2 問題：SQLiteのカラム名を誤認していた

当初、collector作成時にSQLiteのカラム構造を推測して処理していたため、実際には存在しないカラムを参照する問題が発生した。

そこで以下を実行して実際のスキーマを確認した。

```sql
PRAGMA table_info(connections);
```

実際の主要カラムは以下であった。

```text
connection
connection_type
connection_transport
connection_protocol
connection_timestamp
connection_root
connection_parent
local_host
local_port
remote_host
remote_hostname
remote_port
```

特に送信元IPは、

```text
remote_host
```

であった。

### 改善点

今後はSQLiteベースのログ解析を行う際、推測でSQLを書くのではなく、最初に必ず

```sql
PRAGMA table_info(...)
```

を実行してスキーマを確認する必要がある。

## 4.3 問題：HTTPプロトコル名が想定と異なった

collectorでは当初、

```text
http
tls
```

をHTTP系プロトコルとして想定していた。

しかしSQLiteを実際に確認すると、

```text
httpd
```

として保存されていた。

例えば以下のようなデータである。

```text
httpd|145.220.91.19|80
httpd|185.12.59.118|443
```

そのため、

```python
if protocol not in ("http", "tls"):
```

のような条件では対象がすべて除外され、

```text
Collected: 0 events
```

となっていた。

### 対応

以下を対象に含めた。

```python
("httpd", "http", "tls")
```

これによりSQLiteのWeb接続を正しく取得できるようになった。

---

## 4.4 問題：巨大なDionaeaログを毎回全読み込みしていた

VPS2のDionaeaログは約700MB以上あり、約669万行存在していた。

初期collectorでは、

```python
f.readlines()
```

を使用してログ全体をメモリへ読み込んでいた。

この方式では、

- 実行時間が長い
- メモリ消費が大きい
- 30分cron運用に適さない

という問題があった。

### 対応

ログの現在位置を保存する方式に変更した。

```text
state/log_position.json
```

に前回のファイル位置を保存し、

```python
f.seek(start)
```

で前回以降に追記された部分だけを解析するように変更した。

これにより、

```text
過去ログ全体
```

ではなく、

```text
直近30分程度で増えた部分
```

のみを処理できるようになった。

# 10. VPS4で発生した重大問題：OOM Killer

VPS2用collectorをベースにVPS4で初回実行したところ、

```text
Killed
```

となり、Pythonプロセスが強制終了した。

当初は単なるPythonエラーにも見えたため、以下でシステム状態を確認した。

```bash
free -h
```

結果：

```text
Mem: 1.9Gi
Swap: 0B
```

さらに、

```bash
sudo dmesg | tail -30
```

を確認した結果、以下が記録されていた。

```text
oom-kill
Out of memory: Killed process ... python3
anon-rss:1576592kB
```

### 原因

Pythonのcollectorが約1.5GBの物理メモリを使用していた。

VPS4はRAM約2GB、Swapなしであり、LinuxのOOM KillerがPythonを終了させていた。

主な原因は以下である。

1. Dionaeaログが約1.3GB存在
2. SQLite connectionsが約21万件存在
3. VPS2用collectorの全件読み込み方式をそのまま使用
4. `f.readlines()` によるログ大量読み込み
5. SQLite大量データのメモリ保持

# 11. VPS4 OOM対策

以下の2点を変更した。

## 11.1 ログ位置を現在末尾へ設定

Dionaeaログサイズ：

```text
1385420843 bytes
```

を取得し、

```text

```

へ保存した。

```json

  "position": 1385420843
}
```

これにより過去1.3GBを初回から処理せず、運用開始以降に追加されたログだけを見るようにした。

## 11.2 SQLite取得件数制限

全件SELECTをやめ、

```sql

```

とした。

これによりメモリ使用量を大幅に削減した。

# 13. VPS4で発生した問題：9時間の時刻ずれ

VPS4でテストとして以下を実行した。

```bash
nc -vz 127.0.0.1 23
```

Dionaeaログには、

```text
[10082026 00:29:53]
```

と記録された。

SQLite側でも、

```text
2026-08-10 00:29:53|172.18.0.1|23|Blackhole
```

となっていた。

しかしcollectorでは、

```text
Collected: 0 events
```

となった。

### 原因

collectorの `parse_log_time()` ではDionaeaログの時刻をJSTとして扱い、

```text
JST → UTC
```

変換していた。

しかし実際にはDionaeaログ自体がUTCであった。

そのため、

```text
ログ 00:29
```

を誤ってJSTと判断して9時間前へ変換してしまい、SQLiteの接続時刻との時間差が大きくなっていた。

collectorではSQLiteとログの時刻差を120秒以内としていたため、IPとの紐付けに失敗していた。

### 対応

Dionaeaログ時刻を最初からUTCとして処理するように修正した。

```python
return dt.replace(tzinfo=timezone.utc)
```

この修正後、

```text
Collected: 1 events
```

となり、正常にイベントを取得できた。

# 27. 今回の構築で得られた知見

今回の構築で特に重要だった点は、単純にログファイルを読み込むだけでは長期運用に耐えないことである。

初期段階では、

```text
全ログ読込
全DB読込
全イベント処理
```

という方式でも少量データでは動作した。

しかし、VPS4では約1.3GBのログと21万件以上の接続履歴が存在し、実際にOOMが発生した。

そのため、

```text
ログ位置管理
最新DBのみ取得
送信元IP重複除外
定期処理
```

といった継続運用を前提とした処理へ変更する必要があった。
