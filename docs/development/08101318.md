# 開発日記  
## Dionaeaログ収集経路の再設計からAI解析cron開始まで

## 1. 今回の開発目的

今回の開発では、VPS2・VPS3・VPS4に配置しているDionaeaハニーポットのログ収集経路を再確認し、VPS1へログを集約してAIによる解析レポートを自動生成するところまでのシステムを構築した。

今回使用するVPSの役割は以下の通りである。

| VPS | 役割 | 主な監視対象 |
|---|---|---|
| VPS1 | ログ集約・AI解析サーバ | VPS2～VPS4から収集したログ |
| VPS2 | Web系ハニーポット | HTTP/HTTPS系アクセス |
| VPS3 | DB系ハニーポット | MySQL/MSSQL系アクセス |
| VPS4 | IoT系ハニーポット | Telnet/MQTT/UPnP系アクセス |

なお、TailscaleのIPアドレス、SSHポート番号など、外部へ公開する必要のない接続情報は本日記では記載しない。

---

# 2. ログ収集設計の見直し

## 2.1 当初のログ収集設計

当初は、各VPSにWazuh Agentを配置し、各ハニーポットで発生したログをWazuh Agent経由でVPS1のWazuh Managerへ集約する構成を考えていた。

当初想定していた流れは概ね以下である。

```text
VPS2 / VPS3 / VPS4
        ↓
Dionaeaログ
        ↓
Wazuh Agent
        ↓
VPS1 Wazuh Manager
        ↓
Wazuh Decoder / Rule
        ↓
Wazuh側で生成されたログ
        ↓
AI解析
```

この方式では、Wazuhでデコードやルール判定を行った後のログをAI解析へ使用することを想定していた。

しかし、実際に各VPSのログ経路を確認すると、Wazuhによる変換後のログだけでは、Dionaeaが元々保持している情報との対応関係を確認しにくいという問題があった。【問題1】

また、卒業研究では将来的に、

```text
元ログ
AI解析
手動解析
```

を比較する必要がある。

そのため、Wazuhで処理された後のデータだけを保存するのではなく、Dionaeaが実際に出力したログを基準データとして扱う方が適していると判断した。

---

## 2.2 ログ収集設計の変更

そこで設計を変更し、**Wazuhで解析・変換された結果を主な解析対象とする方式から、Dionaeaが直接出力したログを収集する方式**へ変更した。

設計変更後の基本的な考え方は以下である。

```text
Dionaea
   ↓
Dionaeaが直接出力したログ
   ↓
ログ収集
   ↓
VPS1へ集約
   ↓
必要な情報を抽出・正規化
   ↓
AI解析
```

各VPSには引き続きWazuh Agentを配置し、Dionaeaが生成したログをVPS1へ集約できる構成を維持する。

一方、今回構築したAI解析用の処理では、各VPS上に存在するDionaeaのログファイルおよびSQLiteを直接確認し、

```text
collect_dionaea.py
```

によって必要な情報を抽出・正規化した後、JSONとしてVPS1へ転送する方式を採用した。

つまり、今回の開発によって、

```text
Wazuhが解析した結果のみをAIへ渡す
```

のではなく、

```text
Dionaeaが取得した元データ
        ↓
必要情報をこちらで抽出
        ↓
正規化JSON
        ↓
AI解析
```

という構成へ変更した。

この変更により、WazuhのルールやDecoderの結果だけに依存せず、元ログを基準としてAI解析と手動解析を比較できるようになった。

# 3. 各VPSの現状把握

設計変更後、最初にVPS2・VPS3・VPS4について、

- Dionaeaが稼働しているか
- どのポートを公開しているか
- Dionaeaログがどこにあるか
- SQLiteがどこにあるか
- ログ容量に問題がないか
- Wazuh Agentが動作しているか

を確認した。

主に以下のコマンドを使用した。

```bash
sudo docker ps
sudo ss -tulpn
find ~/ -name "dionaea.log" 2>/dev/null
sudo docker exec <container> find / -name "*.sqlite" 2>/dev/null
df -h
du -sh ~/honeypot/*
```

この調査によって、DionaeaのログファイルとSQLiteの保存場所がVPSごとに必ずしも同じ扱いになっていないことが分かった。【問題2】

---

# 4. ディスク容量とログサイズの確認

各VPSの状態を調査する中で、Dionaeaログが非常に大きくなっているVPSが存在することが分かった。

過去の確認では、一部VPSで約40GBのディスクの大部分が使用されており、Dionaeaログ単体で数十GB規模まで増加していたことも確認した。【問題3】

この状態で、

```python
readlines()
```

などを利用してログ全体を毎回処理すると、

- メモリ使用量増大
- collector実行時間増加
- cron処理の遅延
- VPS自体の停止

につながる可能性がある。

そこで、今回のcollectorではログ全体を毎回処理するのではなく、前回読み込んだ位置を保存して差分だけを処理する方式を採用することとした。

# 5. Dionaea SQLiteの探索

Dionaeaの接続情報には、

- 送信元IP
- 接続先ポート
- プロトコル
- 接続時刻

などがSQLiteへ保存されている。

そのため、ログファイルだけでなくSQLiteの確認も必要となった。

コンテナ内を探索したところ、Dionaeaが実際に使用しているSQLiteは、

```text
/opt/dionaea/var/lib/dionaea/dionaea.sqlite
```

に存在することを確認した。

しかしVPS2では、

```text
/tmp/dionaea.sqlite
```

に存在していた過去のコピーをcollectorが参照していた。【問題4】

このSQLiteは最新のDionaeaとは連動しておらず、

```text
Dionaeaログには攻撃がある
        ↓
古いSQLiteには接続が存在しない
        ↓
src_ipを取得できない
```

という状態になっていた。

---

# 6. SQLiteのホスト側への永続化

そこで、Dockerコンテナ内部だけに存在するSQLiteを、ホスト側から常時参照できるように変更した。

docker-compose.ymlへ、

```yaml
- ./dionaea/data:/opt/dionaea/var/lib/dionaea
```

を追加した。

既存のSQLiteについては、

```bash
sudo docker cp \
<container>:/opt/dionaea/var/lib/dionaea/dionaea.sqlite \
~/honeypot/dionaea/data/
```

によってホスト側へ移動した。

さらに、

```bash
sudo chown -R ubuntu:ubuntu ~/honeypot/dionaea/data
```

によって権限を調整した。

この処理を行うことで、collectorから、

```text
/home/ubuntu/honeypot/dionaea/data/dionaea.sqlite
```

を参照できるようになった。

この経験から、SQLiteを利用する処理では最初に必ず実際のスキーマを確認する方針とした。


```text

```

```text

```

これによりWeb系接続を取得できるようになった。

# 10. VPS2ログの差分読み込み

VPS2のDionaeaログも非常に大きくなっていた。

初期collectorではログをまとめて、

```python
f.readlines()
```

で取得していた。

しかし長期間のログを毎回読み込む方式はcron運用に適さない。

そこで、

```text
state/log_position.json
```

を作成し、

```text
前回読み込んだbyte位置
```

を保存する方式へ変更した。

次回は、

```python
f.seek(position)
```

から処理を開始する。

これにより、

```text
全ログ
```

ではなく、

```text
前回実行後に追加されたログ
```

のみを解析できるようになった。【問題7】

# 11. 送信元IPの24時間重複除外

同じIPから短時間に大量の攻撃が発生すると、AIへ送るデータが同一攻撃元で偏る。

そこで、

```text
state/analyzed_ips.json
```

を作成した。

一度解析対象にしたIPについて、

```text
IP
最後に解析した時刻
```

を保存する。

前回解析から24時間以内の場合は、新しいAI解析対象から除外する。

これにより、同一IPによる大量アクセスがAI解析枠を占有することを防いだ。

# 14. VPS4でのメモリ不足

VPS2のcollectorを基にVPS4で処理を実行したところ、

```text
Killed
```

と表示され、Pythonが突然終了した。

最初はPython側のエラーも疑ったが、

```bash

```

を確認した結果、

```text

Out of memory

```

が記録されていた。

Pythonプロセスは約1.5GBのメモリを使用していた。【問題9】

VPS4は約2GBのRAMでSwapが設定されていなかったため、LinuxのOOM Killerによってcollectorが停止していた。

# 15. VPS4のOOM対策

VPS4では、

- Dionaeaログが約1GBを超えている
- SQLiteに約21万件以上の接続情報が存在する

状態であった。

そこでSQLiteの全件取得をやめ、

```sql
ORDER BY connection_timestamp DESC
LIMIT 10000
```

として最新の接続だけを読み込むようにした。

また、ログファイルについても、

```text
現在のファイル末尾
```

を `log_position.json` の初期値とし、過去の巨大ログを初回から解析しない方式へ変更した。

さらに、`readlines()` を使用せず、逐次的に行を読むように変更した。

これによりOOMを回避できた。

# 17. DionaeaログとSQLiteの時刻ずれ

VPS4でTelnetテスト接続を行った。

DionaeaログとSQLiteを比較すると、どちらも、

```text
00:xx:xx
```

のような同じ時刻を記録していた。

しかしcollectorでは、

```text
Collected: 0 events
```

となった。

原因を確認したところ、collector側ではDionaeaログの時刻をJSTとして解釈した後にUTCへ変換していた。

実際にはDionaeaログ自体がUTCで記録されていたため、9時間のずれが発生していた。【問題11】

そこで、

```python
dt.replace(tzinfo=timezone.utc)
```

として、DionaeaログをそのままUTCとして扱うように変更した。

修正後、

```text
Collected: 1 events
```

となり、SQLiteとの照合に成功した。

---

# 18. 時刻だけでなくポートも利用した照合

ログとSQLiteを時刻だけで照合すると、同じ時刻付近に複数の攻撃が存在する場合、別の接続を誤って取得する可能性がある。

そこでDionaeaログに記録される、

```text
[ローカルIP:ポート -> リモートIP:ポート]
```

から `local_port` を抽出した。

SQLiteとの照合を、

```text
timestamp
+
local_port
```

で行う方式へ変更した。【問題12】

これにより、同時刻付近に複数サービスへの接続が存在しても、より正確に攻撃元IPを対応付けられるようになった。

# 28. 発生した問題一覧

## 問題1：Wazuh解析後ログだけでは元ログとの対応を確認しにくい

### 内容

当初は各VPSのログをWazuh AgentからVPS1へ送り、Wazuh Manager側で解析された結果をAI解析に使用する構成を考えていた。

しかし、WazuhのDecoderやRuleによる処理後のログだけでは、Dionaeaが実際に取得した元データとの対応関係を確認しにくかった。

また、手動解析とAI解析を比較する研究では元ログそのものを保持する必要がある。

### 対応

Dionaeaが直接生成したログおよびSQLiteを基準とする方式へ変更した。

各VPSのcollectorで必要な情報を正規化し、VPS1でAI解析を行う構成とした。

---

## 問題2：DionaeaログとSQLiteの保存場所が分かりにくかった

### 内容

DionaeaはDockerコンテナで動作していたため、

```text
ホスト側
コンテナ内部
```

の両方にログ関連ファイルが存在していた。

過去にコピーしたファイルも残っていたため、どのファイルが実際に更新されているのか判断しにくかった。

### 対応

```bash
find
docker exec
docker cp
```

などを用いて実際のファイル位置を調査した。

---

## 問題3：Dionaeaログによるディスク容量圧迫

### 内容

Dionaeaログが長期間保存され続け、一部VPSではディスク容量の大部分をログが占有していた。

過去の確認では、約40GB規模のディスクで数十GBのDionaeaログが存在する状態も確認した。

### 対応

巨大ログを毎回解析する方式をやめ、差分読み込み方式を採用した。

今後はログローテーションおよび保存期間についても設計する必要がある。

## 問題4：古いSQLiteファイルを参照していた

### 内容

VPS2では `/tmp` に存在するSQLiteを利用していたが、これは以前コンテナからコピーしたファイルであり、現在のDionaeaとは連動していなかった。

そのため、

```text
最新Dionaeaログ
≠
SQLiteの接続情報
```

となり、送信元IPを取得できなかった。

### 対応

Docker volumeを追加し、Dionaeaが実際に利用するSQLiteをホスト側に永続化した。

---

## 問題5：SQLiteのカラム名を推測していた

### 内容

実際のスキーマを確認せずにSQLを作成したため、存在しないカラムを参照する問題が発生した。

### 対応

```sql
PRAGMA table_info(connections);
```

を実行して、

```text
remote_host
local_port
connection_timestamp
connection_protocol
```

などの実カラムを確認した。

## 問題6：HTTPプロトコル名が想定と異なった

### 内容

HTTP接続を `http` と想定していたが、Dionaea SQLiteでは `httpd` と保存されていた。

そのためcollectorがWebイベントを除外していた。

### 対応

実際のSQLiteデータを確認し、`httpd` を対象へ追加した。

## 問題7：巨大ログを一括読み込みしていた

### 内容

初期collectorで `readlines()` を使用していたため、ログサイズの増加とともにメモリ使用量と処理時間が増加した。

### 対応

`log_position.json` に前回の読み込み位置を記録し、差分だけを読み込む方式へ変更した。

## 問題8：VPS3のDBサービスが正常待受していなかった

### 内容

DockerではMySQL/MSSQL向けポートを公開していても、Dionaea内部のサービス設定が正しくなければ実際には接続を受け付けない状態となっていた。

### 対応

Dionaeaのサービス設定ファイルを確認・修正し、コンテナ内外から接続可能であることを確認した。

## 問題9：VPS4でOOM Killerが発生した

### 内容

VPS4でcollectorを実行すると、

```text
Killed
```

となった。

`dmesg` によりPythonプロセスが約1.5GBのRAMを使用し、OOM Killerによって終了されたことを確認した。

VPS4は約2GB RAM、Swapなしであった。

### 対応

- SQLiteの取得件数を制限
- 最新接続だけを利用
- 巨大ログを差分読み込み
- `readlines()`を廃止

した。

## 問題10：Web用collectorをIoTへそのまま流用できなかった

### 内容

VPS2はWeb用であり、VPS4はTelnet/MQTT/UPnP用である。

そのためポートやプロトコル条件が異なり、VPS2用コードではVPS4の接続を取得できなかった。

### 対応

VPS4専用のIoTサービス分類を追加した。

## 問題11：ログ時刻をJSTと誤認した

### 内容

Dionaeaログの時刻をJSTと判断してUTC変換していたが、実際にはログ自体がUTCだった。

その結果SQLiteとの間に9時間のずれが発生した。

### 対応

Dionaeaログを最初からUTCとして扱うよう修正した。

## 問題12：時刻だけのログ照合では誤対応の可能性があった

### 内容

同じ時刻付近に複数ポートへの接続が存在すると、時刻だけでは別の攻撃元IPを選択する可能性があった。

### 対応

```text
timestamp
+
local_port
```

の2条件でSQLiteと照合する方式へ変更した。

## 問題13：ログ転送とAI解析が同時実行される可能性があった

### 内容

### 対応

各VPSを00分・30分、VPS1を05分・35分として5分の余裕を持たせた。

## 問題14：VPS1のcronサービスが停止していた

crontabへの登録自体は成功していたが、cronデーモンが停止していた。

そのため登録した処理が実行されない状態だった。

### 対応

cronサービスを起動し、自動起動を有効化した。

その後、実際にAI解析レポートがcronから生成されることを確認した。

# 29. 今回の開発で得られた知見

今回特に大きかった知見は、ログ収集基盤を構築する際に、最初からWazuhの解析結果だけを見るのではなく、**ログを生成しているDionaeaそのものまで遡って確認する必要がある**という点である。

今回の問題の多くは、

```text
実際のログ形式
SQLiteの実データ
Docker内のファイル位置
ログ容量
時刻形式
プロトコル名
```

を推測して処理したことで発生していた。

今後は、

```text
1. 稼働サービス確認
2. 元ログ確認
3. 保存場所確認
4. SQLiteスキーマ確認
5. 実データを少量確認
6. collector作成
7. 転送確認
8. cron化
```

の順番で構築する。

今回の設計変更によって、今後の卒業研究で必要となる、

```text
元ログ
↓
手動解析
↓
AI解析
↓
解析結果比較
↓
高品質データ抽出
↓
評価用データセット作成
```

へ進むためのログ収集・AI解析基盤が完成した。
