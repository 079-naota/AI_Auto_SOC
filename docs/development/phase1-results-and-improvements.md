# 卒業研究 第1段階の結果と第2段階への改善方針

## 1. 本文書の目的

本書では、卒業研究の第1段階で構築したログ収集・AI解析基盤について、実施内容、得られた結果、明らかになった課題を整理する。さらに、その課題を第2段階でどのように改善するかを示す。

第1段階では、複数のVPSに配置したハニーポットのログを収集し、Wazuhで集約した上で、AIによる解析レポートの生成と学習用データセットへの変換を試みた。この実験によって一連の処理基盤は成立したが、ログ収集期間、観測できる攻撃段階、AIへの入力単位に課題が残った。

## 2. 第1段階の目的

第1段階の目的は、次の処理を連続して実行できる基盤を構築することであった。

1. インターネットからハニーポットへ到来する通信を記録する
2. 各VPSのログをVPS1へ集約する
3. 元ログをAIへ入力できる形式へ整形する
4. AIによる攻撃内容の解析レポートを生成する
5. 元ログ、手動解析結果、AI解析結果から学習用データセットを作成する

## 3. 第1段階の構成

第1段階では、VPS1を管理・解析ノードとして使用し、VPS2～4を異なる攻撃経路を観測するハニーポットとして使用した。

| 機器 | 主な役割 |
| --- | --- |
| VPS1 | Wazuh Manager、Cowrie、ログ集約、AI解析、データセット作成 |
| VPS2 | Web系Dionaea、Wazuh Agent |
| VPS3 | DB系Dionaea、Wazuh Agent |
| VPS4 | IoT系Dionaea、Wazuh Agent |

基本的な処理経路は次のとおりである。

```text
インターネットからの通信
        ↓
VPS1～4のハニーポット
        ↓
ハニーポットの元ログ
        ↓
VPS1への収集・正規化
        ↓
手動解析とAI解析
        ↓
解析結果の比較
        ↓
学習・評価用データセット
```

当初はWazuhによる変換後のログをAI解析へ使用する構成を想定していた。しかし、変換後のログだけでは、ハニーポットが実際に取得した情報との対応関係を確認しにくかった。そのため、最終的にはDionaeaなどが直接生成した元ログを基準データとして収集・正規化する方式へ変更した。

## 4. 第1段階で実現したこと

### 4.1 ハニーポットログの収集

- Cowrieの接続、認証、コマンド入力をJSON形式で記録した
- DionaeaのWeb、DB、IoT系ログを各VPSで取得した
- Wazuh AgentからVPS1のWazuh Managerへログを送信した
- WazuhのDecoderとRuleだけに依存せず、ハニーポットの元ログを保存した
- ログの肥大化に備えてローテーションを設定した

### 4.2 AI解析の自動化

- VPS1で定期的に元ログを収集する処理を構築した
- Gemini APIへログを入力し、解析レポートを生成した
- 解析結果をMarkdownやJSONとして保存した
- cronを利用して収集から解析までを定期実行した

### 4.3 データセットの作成

元ログ、手動解析結果、AIレポートを整理し、次の出力項目を持つJSONLデータセットへ変換した。

- `activity`：観測した活動の概要
- `severity`：危険度
- `success`：成功、失敗、判断不能
- `evidence`：判断根拠
- `uncertainty`：現在のログでは判断できない点
- `confidence`：判断の確度

AIが生成した結果を無条件に正解データとせず、人間が確認したデータを`gold`、未確認のAI結果を`pseudo`、正解のないログを`unlabeled`として分離した。

## 5. 第1段階の結果

### 5.1 データセット生成結果

品質検査後に確定したgoldデータは144件であった。学習、検証、テストの分割結果を以下に示す。

| データ | 件数 |
| --- | ---: |
| gold全体 | 144 |
| 学習データ | 100 |
| 検証データ | 22 |
| テストデータ | 22 |

ハニーポット別のgoldデータ件数は次のとおりであった。

| 収集元 | 件数 |
| --- | ---: |
| Web | 14 |
| DB | 29 |
| IoT | 86 |
| Cowrie | 15 |

危険度と攻撃成否の分布を以下に示す。

| 項目 | 分布 |
| --- | --- |
| `severity` | low 128件、medium 9件、high 7件 |
| `success` | unknown 134件、success 5件、failure 5件 |

`success=unknown`は144件中134件であり、全体の約93.1%を占めた。この結果はデータ生成処理の失敗ではなく、第1段階の監視方式では、要求やコマンドの入力後に実際のシステムで何が起きたかを十分に確認できなかったことを表している。

### 5.2 ラベルの品質管理

データセット作成時には、次のデータを分離した。

| 種類 | 件数 | 取扱い |
| --- | ---: | --- |
| 人間確認済みgold | 144 | 学習・検証・テストに使用 |
| Cowrieの未確認擬似ラベル | 109 | goldへ混ぜず別管理 |
| Cowrieの未ラベルデータ | 345 | 初回学習の対象外 |
| VPS2～4のAI比較データ | 60 | 手動解析との比較専用 |
| 除外記録 | 429 | 除外理由を記録して保存 |

学習、検証、テスト間では、送信元IPの重複と内容ハッシュの重複がともに0件であることを確認した。これにより、同一攻撃の特徴が学習データと評価データの両方へ混入するデータ漏洩を防止した。

### 5.3 攻撃ログの傾向

第1段階では、認証試行、ポート探索、既知のパスへのHTTPリクエストなど、自動化されたスキャンや探索活動が多く観測された。一方、ログイン後のコマンド実行結果、ファイル変更、プロセス生成など、侵入後の挙動を確認できるログは少なかった。

手動確認では、収集した活動のおよそ9割が自動スキャンや探索に該当すると判断した。ただし、この割合を最終的な研究結果として使用する場合は、スキャンの分類基準、集計対象期間、総セッション数を明記した上で再集計する必要がある。

## 6. 第1段階で得られた知見

### 6.1 元ログを基準にする必要がある

WazuhのDecoderやRuleによる処理後の情報だけでは、ハニーポットが取得したすべての情報を確認できない場合があった。AI解析や手動解析の検証可能性を保つためには、加工前の元ログを保存し、その元ログから正規化データを作成する必要がある。

### 6.2 ログ保存設計が必要である

一部のVPSではDionaeaログが数十GB規模まで増加し、ディスク容量を圧迫した。長期間のログ収集には、ログローテーション、圧縮、保存期間、バックアップ先を事前に決める必要がある。

### 6.3 実データによる設定確認が必要である

第1段階では、次の問題を確認した。

- 実際に使用されていない古いSQLiteファイルを参照していた
- Dockerでポートを公開していても、コンテナ内のサービスが待ち受けていない場合があった
- DionaeaログをJSTとして処理したため、SQLiteとの間に9時間のずれが発生した
- 想定したプロトコル名と実データ上の表記が異なっていた

この経験から、サービス状態、元ログ、保存場所、データ形式、時刻形式を実データで確認してから収集処理を実装する必要があると分かった。

## 7. 第1段階の主要な課題

### 7.1 ログ収集期間が短い

第1段階のログ収集期間は約1か月であった。そのため、攻撃種類、送信元、時間帯の偏りを十分に評価できず、継続的な攻撃や頻度の低い攻撃を収集できなかった可能性がある。

### 7.2 ログ品質が低い

収集ログの多くは、接続、認証試行、スキャン、攻撃コマンドの送信までの記録であった。攻撃後にプロセスが実行されたか、ファイルが変更されたか、ペイロードが動作したかを確認できないため、攻撃成否の大部分を`unknown`とする必要があった。

特に、攻撃者がコマンドを送信したことと、そのコマンドが実際に成功したことを区別できない点が課題である。

### 7.3 AIレポートの解析単位が粗い

第1段階では、一定時間内の複数の送信元IPをまとめてAIへ入力する場合があった。その結果、次の問題が生じた。

- 異なる攻撃者の活動が同一レポートへ混在する
- レポート全体の危険度を個別IPへ適用できない
- どのログを根拠に判断したか分かりにくい
- 手動解析結果との比較が難しい
- 学習データへ変換する際にIP別のラベルを再構成する必要がある

## 8. 第2段階の改善方針

第1段階の課題と第2段階の改善方法を以下に示す。

| 第1段階の課題 | 第2段階の改善 |
| --- | --- |
| 収集期間が約1か月 | 2026年10月5日から12月25日まで継続収集する |
| 認証試行やスキャン中心 | Cowrie Proxyと隔離Linuxバックエンドを導入し、侵入後の操作を観測する |
| 攻撃成否を確認できない | Suricata、auditd、Wazuh FIMを組み合わせ、通信・プロセス・ファイル変更を記録する |
| 複数IPをまとめてAI解析 | 1送信元IP・1攻撃セッションを基本単位にする |
| AIの結論と根拠が曖昧 | 根拠、不確実性、信頼度を構造化して出力する |

## 9. 第2段階の構成

### 9.1 VPS1：管理・ログ保管・AI解析

- VPS2～4のログを一元管理する
- Cowrie、Suricata、auditd、FIMのログを相関する
- 1攻撃セッション単位のデータセットを作成する
- AI解析を実行する
- ログと解析結果を長期保管する

### 9.2 VPS2：低対話型Webハニーポット

- DionaeaでHTTP・HTTPSサービスを模倣する
- 接続情報、リクエスト、送信データを記録する
- Wazuh AgentからVPS1へログを送信する

### 9.3 VPS3：隔離バックエンド

- Cowrie Proxyから接続される実Linux環境として使用する
- auditdで実際のプロセス実行やシステム操作を記録する
- Wazuh FIMで重要ファイルとディレクトリの変更を監視する
- 攻撃用接続元をVPS4に限定する
- 外向き通信を制限し、踏み台化を防止する
- セッション終了後に環境を初期化する

### 9.4 VPS4：Cowrie Proxy・Suricata

- SSH・Telnetへの接続をCowrie Proxyで受け付ける
- 攻撃者のセッションをVPS3の隔離環境へ転送する
- Cowrieで認証、コマンド入力、セッション情報を記録する
- SuricataをIDSとして使用し、通信フローと検知アラートを記録する
- Wazuh AgentからVPS1へログを送信する

## 10. 第2段階のログ相関

第2段階では、1送信元IP・1攻撃セッションを解析単位とする。主に次の情報を使用してログを関連付ける。

- Cowrieのsession ID
- Suricataのflow_id
- 送信元・宛先IPアドレス
- 送信元・宛先ポート
- セッション開始・終了時刻
- auditdのイベント時刻とプロセス情報
- Wazuh FIMの変更時刻と対象パス

すべての機器で時刻同期を行い、保存時刻は原則としてUTCへ統一する。

## 11. 第2段階のAI解析

AIへの入力には、同一攻撃セッションへ関連付けられたログだけを使用する。出力項目は次のとおりとする。

- 攻撃活動の概要
- 危険度
- 攻撃の成功、失敗、判断不能
- 判断根拠となったログ
- 現在のログでは判断できない点
- 判断の信頼度

攻撃者がコマンドを入力した事実だけで成功と判定せず、VPS3上でのプロセス実行、ファイル変更、通信結果などを成功判定の根拠とする。

また、インターネットから到来した実攻撃を`real`、研究者が実行した動作確認を`controlled_test`として明確に区別する。

## 12. 第2段階の評価項目

第2段階では、次の指標を用いて第1段階からの改善を評価する。

- 収集した攻撃セッション数
- 侵入後操作を含むセッション数
- ログ相関に成功したセッションの割合
- `success`または`failure`を根拠付きで判定できた割合
- `unknown`の割合
- AIと手動解析の一致率
- AIが提示した根拠の正確性
- 複数IPの活動が混在したレポートの件数
- 1セッション当たりの解析時間

## 14. まとめ

第1段階では、ハニーポットの元ログを収集し、手動解析、AI解析、データセット作成までを実行する基盤を構築した。品質検査済みのgoldデータ144件を作成し、学習・検証・テスト間のIPおよび内容の重複がない状態で分割できた。

一方、収集期間が短く、認証試行やスキャンが中心であったため、攻撃成否の約93.1%を判断できなかった。また、複数IPをまとめたAI解析では、個別攻撃者の活動と判断根拠を明確に対応付けられなかった。

第2段階では、Cowrie Proxy、隔離Linuxバックエンド、Suricata、auditd、Wazuh FIMを組み合わせ、攻撃入力だけでなく実際のシステム変化まで観測する。さらに、1送信元IP・1攻撃セッション単位でログを相関し、AI解析と手動解析を比較することで、第1段階より高品質なデータセットと説明可能なAIレポートの作成を目指す。
